Chapter 01 / Arrive ready

Bring a safe example, not the client’s secrets.

The event builds on a repository from the previous session. If you have it, open it before the call. If you do not, you can still follow the decisions without recreating last week’s work.

Choose one harmless change: clarify a README step, rename a sample output, or tighten a validation rule. It should be small enough that another person can explain what changed.

Your first useful question

“What must still be true after this change?” That answer becomes the delivery contract.

A delivery contract here means the agreed behavior and boundaries of the workspace—not a substitute for a legal agreement.

Before the call

These ticks stay in this browser when storage is available. They do not configure a repository.

Quick vocabulary

Branch: a separate line of work. Commit: a recorded change. Pull request (PR): a proposed change for review. CI: automated checks on changes. Continuous delivery: keeping tested changes ready to release; it does not have to mean automatic production use.

Chapter 02 / Define the promise

“Safe” needs a testable meaning.

Imagine a workspace that prepares a draft delivery package. It may read approved sample files and write a draft. It must not contact a client or copy credentials into that package.

Write three plain rules

  1. Allowed input: only the agreed sample folder.
  2. Expected output: a draft with the required fields.
  3. Forbidden action: no external send or production write without approval.

Tests can check output shape and reject disallowed paths. Other controls must constrain credentials, network access and runtime permissions. A green test suite only covers what you actually checked.

Evidence to look for

  • A plan check: scope, acceptance condition and risk noted.
  • A test that fails when a required output field disappears.
  • A secret scan that reports a harmless fixture.
  • A required check that prevents the PR from merging.
How a check becomes a real gate

Creating a workflow does not make its result mandatory. Branch protection or rulesets must require the relevant checks and reviews. Review bypass permissions too; administrators can be exempt unless restrictions are configured. Confirm the failure blocks an actual merge attempt, not just that a red icon exists.

Source: GitHub: protected branches. Consult the official documentation for your repository type and plan.

A useful gate says “not yet.”

Try a change below. Notice that passing checks and human review are different steps. Changing the example clears every later approval.

Local rehearsal. These are predefined teaching scenarios—not GitHub runs, a secret scanner, or a real merge. No code executes and no credentials are needed.

The change removes a required field from the draft package.

Checks not runChoose a scenario, then run the rehearsal.

A passing run and a review are both needed.

Secret scanning is not a no-leak guarantee

A post-commit secret-scanning alert detects a possible exposure; it is not automatically a merge-blocking check. Push protection blocks supported secret patterns at push time. A required CI scan can be another layer. Each has coverage limits and bypass behavior. Never use a live token to demonstrate failure.

If a real credential is exposed, revoke or rotate it promptly. Deleting the visible line alone does not make the credential safe.

Sources: GitHub: secret scanning · push protection · secure workflow use.

Chapter 04 / Cross two gates

Available is not the same as authorized.

A release names a version and packages the work. Operator permission answers another question: may this exact artifact run in this client context, for this purpose?

The release record

Keep the version, exact commit, check results, package fingerprint, change notes and rollback reference together. A tag alone is not a complete integrity record; verify the artifact you will actually use.

The operational handoff

The event describes a new Mattermost gate between the repo and client folder. Watch for who may approve, what version the approval covers, and what actually stops an unapproved copy or run.

A chat message can record a decision. Enforcement must also live in the delivery path; a visible “approved” label is not enough.

Try the second gate

Complete the healthy-change rehearsal in Chapter 03 first. These controls model permission; they do not grant it anywhere.

No release preparedModel a healthy merge first.

Operator use is not authorized in the model.

What a real approval must bind to
  • Exact version, commit and verified artifact fingerprint.
  • Named approver, operator, destination and permitted action.
  • Approval time, expiry or revocation condition and rollback owner.
  • Reapproval if the artifact, scope or destination changes.

GitHub environment protection can require approval before a deployment job proceeds. Availability depends on plan and repository visibility; required reviewers on GitHub Free are for public repositories. Mattermost integration and a client-folder gate are project-specific work, not automatic GitHub features.

Sources: GitHub: releases · deployment protection and environments.

Chapter 05 / Follow the session

Watch the failure, then the recovery.

This is a suggested observation plan for the 45-minute event—not a confirmed host schedule. If you are presenting, it can double as a rehearsal outline.

00–05

Name the delivery contractWhat should the workspace do, and what must it never do?

05–15

Show checks on a proposed changeLook for a scope check, tests and a scan. Ask which ones are required.

15–25

Break something safelyUse synthetic fixtures. Observe a genuinely blocked PR, fix the change, rerun, then review the latest version.

25–35

Package the exact versionFollow the commit into the release. Identify the artifact, notes, evidence and rollback point.

35–42

Test the operational stopDoes the client-folder delivery fail without approval? Can stale approval authorize a newer artifact?

42–45

Capture one principle to reuseWhat did the system prevent, who made the final decision, and what evidence proves it?

If you are running the demo

Prepare a known-good baseline and two harmless failing changes. Keep client data, tokens and private notifications off-screen. Have a recording or screenshot fallback clearly labelled as prior evidence. Do not spend the session repairing live production infrastructure.

Finish by showing an actual denied attempt and a permitted attempt for the same approved version. Explain any manual or unconnected step plainly.

Chapter 06 / Take it with you

Leave with one change you can defend.

Three questions worth asking

  1. “What prevents merging when a required check fails—and who can bypass it?”
  2. “What prevents an operator using a release before client-context approval?”
  3. “How do we prove the approved artifact is the one that ran?”
The principle to keep

Separate the evidence that a change works from the authority to use it. Neither replaces the other.
